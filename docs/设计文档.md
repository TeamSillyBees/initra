# Golang 快速开发脚手架设计文档

## 1. 文档目标

本文档用于指导 Codex 实现一个可复用的 Golang Web API 脚手架。目标是让开发者能够基于该脚手架快速搭建一个具备完整工程能力、适合中大型业务演进的项目。

该脚手架必须解决以下问题：

* 快速初始化新项目
* 统一项目结构与工程约定
* 提供标准化的 API 开发方式
* 提供数据库迁移、SQL 访问、缓存、认证授权、日志、错误处理、配置管理等基础设施
* 支持后续通过“新增模块”的方式持续扩展业务
* 适合作为团队级标准模板长期维护

---

## 2. 项目定位

该脚手架的定位是：

**一个面向中大型 Golang Web API 项目的、垂直切片架构、契约优先、强类型 SQL、可治理的工程模板。**

适用场景：

* 管理后台 API
* 业务中台/服务端 API
* 需要 RBAC 权限体系的系统
* 需要数据库迁移治理的项目
* 需要多级缓存和较强工程规范的项目

非目标：

* 不追求极简 demo 风格
* 不优先服务于纯 ORM 风格开发
* 不优先支持微服务拆分，优先支持“模块化单体”

## 4. 总体架构

### 4.1 架构原则

1. **Gin 负责 HTTP 承载，Huma 负责 API 契约。**
2. **Jet 作为唯一数据库访问技术栈。**
3. **Atlas 作为唯一数据库变更入口。**
4. **业务按模块垂直切片组织，不按 controller/service/repository 横向集中堆放。**
5. **所有公共基础设施集中在 platform 层。**
6. **业务模块只能依赖 platform，不允许跨模块直接访问对方 repository。**
7. **统一错误码、统一日志字段、统一缓存 Key 规则、统一 API 返回结构。**

### 4.2 分层结构

```text
Client
  -> Gin Router
    -> Global Middlewares
      -> Huma API Operations
        -> Application Service
          -> Repository (Jet)
          -> Cache
          -> External Clients
            -> Database / Redis / Third-party
```

### 4.3 推荐架构风格

采用：

* **垂直切片架构（按业务模块组织）**
* **应用服务 + repository 模式**
* **显式依赖注入**
* **平台层与业务层分离**

不采用：

* 纯横向分层目录
* 重 ORM 模式
* 业务代码直接操作 gin.Context

## 6. 模块设计规范

每个业务模块必须采用统一结构：

```text
internal/app/<module>/
├── api/
│   ├── handler.go
│   ├── request.go
│   └── response.go
├── domain/
│   ├── entity.go
│   ├── service.go
│   └── errors.go
├── infra/
│   ├── repository.go
│   ├── cache.go
│   └── policy.go
├── module.go
└── wire.go
```

### 6.1 各层职责

#### api/

负责：

* Huma operation 注册
* 输入输出 DTO
* HTTP 层参数接入
* 调用 service
* 将错误交给统一错误映射器

禁止：

* 写 SQL
* 写复杂业务逻辑
* 直接使用 Redis/DB

#### domain/

负责：

* 领域实体定义
* 核心业务流程
* 业务错误定义
* service 接口与实现

禁止：

* 依赖 gin.Context
* 依赖具体 HTTP 细节

#### infra/

负责：

* Repository 实现
* Cache 实现
* Casbin policy 辅助
* 第三方依赖接入

禁止：

* 编排复杂业务流程

#### module.go

负责：

* 模块对外暴露注册入口

#### wire.go

负责：

* 使用 do 注册该模块相关依赖

## 8. HTTP/API 设计规范

### 8.1 API 风格

采用 REST 风格。

统一前缀：

* `/api/v1/...`

示例：

* `POST /api/v1/auth/login`
* `GET /api/v1/users/{id}`
* `POST /api/v1/users`
* `PUT /api/v1/users/{id}`
* `DELETE /api/v1/users/{id}`

### 8.2 统一响应结构

成功：

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "trace_id": "xxx"
}
```

失败：

```json
{
  "code": "USER_NOT_FOUND",
  "message": "user not found",
  "details": {},
  "trace_id": "xxx"
}
```

### 8.3 Huma 使用约定

* 所有 API 输入输出模型必须显式定义在 `request.go` / `response.go`
* 所有字段必须写清楚 json tag
* 合理使用校验 tag
* 每个 operation 必须写 summary / description / tags
* 所有 operation 必须自动进入 OpenAPI 文档

### 8.4 上下文传递

* HTTP 层不向 service 传 gin.Context
* 优先传 `context.Context`
* 当前登录用户信息通过 context 注入与提取

## 9. 数据库设计规范

### 9.1 V1 默认数据库

脚手架 V1 默认面向 PostgreSQL 实现。

原因：

* Jet 与 Atlas 对 PostgreSQL 组合成熟
* bigint / timestamp / jsonb / 索引能力完善
* 更适合作为通用业务脚手架默认选型

后续可扩展 MySQL，但 V1 不要求同时兼容多数据库。

### 9.2 表设计约定

所有核心业务表建议包含：

* `id BIGINT PRIMARY KEY`
* `created_at TIMESTAMP NOT NULL`
* `updated_at TIMESTAMP NOT NULL`
* `deleted_at TIMESTAMP NULL`
* `created_by BIGINT NULL`
* `updated_by BIGINT NULL`

如有并发写冲突场景，可增加：

* `version BIGINT NOT NULL DEFAULT 1`

### 9.3 主键策略

* 使用 snowflake 生成 bigint 主键
* 应用层生成 ID，不依赖数据库自增
* 所有外键字段同样使用 bigint

### 9.4 Repository 约定

* 所有 SQL 统一通过 Jet 编写
* 不引入 ORM
* 一个模块一个 repository 文件起步，复杂后可拆分多个 repository
* 查询对象与领域对象可分离

### 9.5 事务约定

* service 层负责事务边界
* repository 不自行开启事务
* 提供统一 `WithinTx(ctx, fn)` 封装

## 10. 数据库迁移与代码生成流程

### 10.1 迁移策略

采用：

* **生产环境使用 Atlas versioned migration**
* **开发阶段允许通过 schema 目标状态辅助生成 migration**

### 10.2 推荐流程

1. 开发者修改目标 schema 或手写迁移意图
2. 生成 migration 文件
3. 本地 apply migration
4. 基于数据库最新状态执行 Jet codegen
5. 开发 repository / service / api

### 10.3 Makefile 命令

必须提供：

```makefile
make migrate-new NAME=create_user_table
make migrate-apply ENV=local
make migrate-status ENV=local
make migrate-diff NAME=add_user_email
make jet
```

### 10.4 生成代码规则

* Jet 生成目录固定为 `internal/gen/jet`
* 生成代码禁止手工修改
* 如需变更，只能通过 schema/migration 后重新生成

## 11. 缓存设计规范

### 11.1 缓存模式

默认支持：

* 本地缓存
* Redis 远程缓存
* 本地 + Redis 多级缓存

### 11.2 适用场景

* 字典类数据
* 权限数据
* 用户详情缓存
* 配置项缓存
* 热点查询缓存

### 11.3 缓存策略

采用 Cache Aside：

* 读：先读缓存，未命中再查库并回填
* 写：先写库，再删除缓存

### 11.4 Key 规范

统一格式：

```text
<app>:<module>:<domain>:<identifier>
```

示例：

```text
myapp:user:profile:1001
myapp:auth:permissions:admin
myapp:dict:country:CN
```

### 11.5 约束

* 不允许在业务代码中硬编码缓存 key
* key 构造必须走统一 helper
* 重要缓存必须配置 TTL
* 必须考虑空值缓存与防穿透

## 12. 认证与授权设计

### 12.1 JWT 设计

提供：

* Access Token
* Refresh Token

建议 Claims：

* `sub`：用户 ID
* `exp`：过期时间
* `iat`：签发时间
* `iss`：签发者
* `roles`：角色列表
* `tenant_id`：可选，多租户时使用

### 12.2 Casbin 设计

V1 采用 RBAC 模型。

建议资源表达：

* `user:create`
* `user:read`
* `user:update`
* `user:delete`
* `role:assign`

或采用对象/动作形式：

* object: `/api/v1/users`
* action: `GET` / `POST` / `PUT` / `DELETE`

V1 推荐：

* **业务权限采用资源动作表达方式**
* 不直接把完整 URL 作为唯一权限语义

### 12.3 鉴权流程

1. JWT 中间件校验 token
2. 提取当前登录用户
3. 加载用户角色/权限信息
4. Casbin 做权限判断
5. 不通过则返回 `FORBIDDEN`

### 12.4 策略存储

V1 推荐：

* 开发环境：文件策略
* 正式环境：数据库策略存储

## 13. 日志设计规范

### 13.1 日志原则

* 全部使用结构化日志
* 日志与错误码体系联动
* 必须能带上 trace_id / request_id / user_id

### 13.2 建议字段

* `trace_id`
* `request_id`
* `user_id`
* `module`
* `operation`
* `path`
* `method`
* `latency_ms`
* `error`

### 13.3 日志级别

* `DEBUG`：开发调试
* `INFO`：正常流程
* `WARN`：可恢复异常
* `ERROR`：业务失败、依赖失败
* `PANIC/FATAL`：仅限启动失败等不可恢复问题

### 13.4 中间件要求

必须实现：

* 请求日志中间件
* Panic Recovery 中间件
* 慢请求日志

## 14. 错误处理规范

### 14.1 错误分层

* 平台错误
* 业务错误
* 参数错误
* 认证错误
* 授权错误

### 14.2 错误码约定

示例：

* `OK`
* `BAD_REQUEST`
* `UNAUTHORIZED`
* `FORBIDDEN`
* `NOT_FOUND`
* `INTERNAL_ERROR`
* `DB_ERROR`
* `CACHE_ERROR`
* `USER_NOT_FOUND`
* `LOGIN_FAILED`

### 14.3 错误使用方式

* 内部使用 `oops` 构建错误
* service 返回业务错误
* web 层统一映射为 HTTP 状态码和响应体
* 不允许直接把底层数据库错误原样暴露给前端

## 15. 配置设计规范

### 15.1 配置来源

按优先级：

1. 默认值
2. 配置文件
3. 环境变量
4. 命令行参数（如实现）

### 15.2 配置结构

建议结构：

```yaml
app:
  name: myapp
  env: local
  port: 8080

http:
  read_timeout: 5s
  write_timeout: 10s

logger:
  level: info
  format: json

database:
  driver: postgres
  dsn: postgres://...
  max_open_conns: 20
  max_idle_conns: 10

redis:
  addr: 127.0.0.1:6379
  password: ""
  db: 0

jwt:
  issuer: myapp
  secret: change_me
  access_token_ttl: 2h
  refresh_token_ttl: 168h

casbin:
  model_path: ./configs/rbac_model.conf
  policy_path: ./configs/rbac_policy.csv

cache:
  local_ttl: 1m
  remote_ttl: 10m
```

### 15.3 配置约束

* 所有配置必须映射到结构体
* 启动时必须做配置校验
* 敏感配置通过环境变量覆盖

## 16. 中间件设计

必须实现以下中间件：

1. Request ID / Trace ID
2. 请求日志
3. Panic Recovery
4. CORS
5. JWT 认证
6. Casbin 授权
7. 统一错误处理

建议中间件顺序：

1. Recovery
2. Request ID
3. Logger
4. CORS
5. Auth
6. Authorization
7. Route Handler

## 17. 脚手架生成能力

该项目不仅是模板仓库，还应带有“生成能力”。

### 17.1 必须支持的生成能力

#### 新建项目

目标：

* 从模板初始化一个新项目目录
* 替换模块名、项目名、Go module 名称、默认配置

#### 新建模块

目标：

* 一键生成模块目录结构
* 生成 handler / DTO / service / repository / cache / policy 文件
* 自动生成模块注册代码模板

#### 新建迁移

目标：

* 一键生成 Atlas migration 模板

### 17.2 推荐实现方式

优先使用项目内脚本实现，不要求引入额外复杂模板引擎。

脚本至少包括：

* `scripts/new_module.sh`
* `scripts/new_module.ps1`
* `scripts/new_migration.sh`
* `scripts/new_migration.ps1`
* `scripts/bootstrap.sh`
* `scripts/bootstrap.ps1`

## 23. Codex 编码约束

Codex 在实现时必须遵守：

1. 不写无用抽象。
2. 优先保证可运行、可读、可扩展。
3. 生成代码与手写代码边界清晰。
4. 不把 gin.Context 传入 domain/service。
5. 不在 handler 中写业务逻辑。
6. 不在 service 中直接拼接缓存 key 字符串。
7. 不使用全局变量存储可替换依赖。
8. 所有基础设施都通过 do 注入。
9. 所有公共错误走统一错误码。
10. 所有公开 API 都必须出现在 OpenAPI 文档中。

## 27. 对 Codex 的最终执行指令
